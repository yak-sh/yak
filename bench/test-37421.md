## Why fixtures alone did not reach the target

The suite still took about 68 seconds after fixture fixes. Deno's `--parallel`
runs native SQLite in threads of **one process**. A V8/native CPU profile of
`work_test.ts` showed SQLite cursor/VM work and mutex lock/unlock overhead. The
decisive controlled comparison used the same four files (`work`, `db`, `mcp`,
`graph_query`), with no overlapping suite:

| Execution                              | Wall s | User s | System s | Start load |
| -------------------------------------- | -----: | -----: | -------: | ---------: |
| One `deno test --parallel`             |   7.10 |  19.63 |     4.59 |       1.96 |
| Four independent `deno test` processes |   4.75 |  15.32 |     0.86 |       0.70 |

Independent native allocators avoid cross-thread SQLite contention. The broad
pass now partitions deterministically into at most `DENO_JOBS` (default CPU
count) independent processes, each running its files sequentially. No test is
skipped or sampled. Shard output is drained concurrently, then printed as
complete reports: interleaved half-lines must not hide durations from
`test:budget`. Partial writes to output pipes are completed too.

A coordinator lives inside the outer runner's owned process group. Its children
do not create new groups. Failure exits the coordinator immediately; the outer
runner settles the whole tree before stopping or starting another phase.
Existing signal overlap/repetition, first-signal ownership and stubborn
descendant coverage remain real process tests; only the grace-period clock is
injected. The separate process-global fixture pass remains sequential.

Eighteen server-importing modules already guard server/HOME/port setup behind
`TASKS_SLOW`. Their fast tests and ignored cases now belong in the broad pass,
not eighteen fresh processes. Under `TASKS_SLOW` they remain isolated. New
server-importing modules remain isolated conservatively until audited.

## Isolation and correctness checks

- `dbFixture` shares only setup bytes and connection-independent metadata, never
  a writable database. Each call deserializes a private image, sharing
  `bareDb`/`freshDb`'s single-live-clone contract. Tests cover one build,
  independent writes, alternating fixture kinds and failed-build retry. The
  original migrated template is now closed after serialization.
- Durable Object SQL cursors are materialized before return. The native
  statement cache is bounded at 256 and finalizes eviction/error entries.
  Main/temp schema versions invalidate cached JS column metadata after DDL,
  including rolled-back DDL. Tests cover bindings, failures, held cursors,
  eviction, scripts, schema change, delete/recreate, rollback and disposal.
- Store disposal belongs to the test that uses it. Helpers returning stores
  transfer that ownership; they must not close a returned handle. A disposed
  storage rejects reads rather than reaching a finalized native statement.
- The FTS stress fixture still inserts all 5,001 additional entries. Real
  migration, CLI process, worker and query assertions remain in place.

The 1 ms advisory/strict budget mechanism is unchanged. This change reduces real
setup, waits and contention; it does not claim every existing test now meets 1
ms.
