# Check regression: repeated blob work (T-37417)

Measured on 2026-09-11 with Deno 2.9.1, 8 available CPUs, no CPU quota
(`cpu.max = max 100000`), and `DENO_JOBS` unset. Logs were captured under
`/tmp/T-37417/` in the investigation session. Times include process startup;
load averages below are the host's one-minute load at command start. These are
local observations, not a cold-CI guarantee.

## Finding

The growing dependency was **check:packages**, not the three input-glob-cached
checks. Commit `58e23790` added
`ten thousand large entries load only a bounded
body window` in
`packages/harness/window_test.ts`. Its 10,000 identical 100 KB bodies represent
1 GB of logical transcript text. Although the blob backend stored that text only
once, the plugin computed SHA-256, checked storage, and resolved the reference
for every row, before the eight-entry read under test.

The unchanged test took 25 seconds inside the first check and 34.55 seconds
isolated (33.70 user CPU seconds). With batch-local interning it took 3.53
seconds isolated (2.79 user CPU seconds). No test size, assertion, timeout, or
coverage was reduced. The optimization applies to real repeated-body writes, not
just fixture construction. Equal strings now share hashing, existence checking,
writing, and reference lookup within one precondition hook. Nothing is retained
across batches or rollbacks; synchronous backends stay synchronous. Regression
tests cover synchronous/asynchronous stores, independently constructed equal
strings, empty strings, zero-valued references, subsequent batches, and
rollback/retry.

The suite wrapper's inner command times for the first three warm runs were
37.733, 22.064, and 23.620 seconds. Higher host load in the after runs did not
erase the improvement. Host load alone is not an explanation: the slow isolated
test spent 33.70 seconds on CPU, while removing repeated work cut that to 2.79
seconds. The control worker's compensation does not model cold type caches or
parallel saturation perfectly; see [suites.md](suites.md). The committed
baseline and 25% tolerance are unchanged. No `SUITE_ACCEPT` was used.

The 20.55-second run demonstrates the compensation limit too: a faster control
sample produced a higher ratio despite less wall time. The wrapper had
automatically banked the earlier 310.99 improvement; its generated baseline
edits were discarded, not committed. The final confirmation used the original
343.58 baseline. Both required gates passed; `DB_PATH=:memory: deno task test`
took 101.91 seconds at starting load 10.98 and emitted its own report-only
timing regression (ratio 1549.21). This change does not claim to fix the broad
suite's separate wall-clock budget.

## Cache behavior

The first fresh-worktree run executed publish/browser/workers. The next run
printed `(cached, inputs unchanged)` for **all three**, even after codegen,
content generation checks, package tests, and suite result recording had run.
Editing `packages/blob/plugin.ts` invalidated all three, as expected: it is a
real shared platform/publish input. After they succeeded, repeated checks again
skipped all three. No input-glob changes are needed. New/rebased source trees
can still incur a real typecheck cost; the warm result is not a promise that all
fresh worktrees finish in the same time.
