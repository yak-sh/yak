One graph, worked by people and agents through the same doors.

yaks is a toolkit of TypeScript packages for storing, querying and rendering records as entities, plus the packages that run agent sessions, tools and tasks over them. yak is its command line, and yaks.app hosts the apps built with it. Every change is an entity patch, and every list is a query. 

deno install -gAf jsr:@yaks/cli/yak

@yaks on JSR Source on GitHub yaks.app

The model

An entity is a record identified by entity.eid, a uuid. Its components are named objects, each describing one aspect of it. There is no kind column: an entity is what its components make it. A task is doc{title, body} plus task{}; a comment is doc plus comment{target}.

bundle
One entity's components as a JSON object: {entity: {eid}, doc: {title}}.
batch
A list of changes applied in one transaction. Each component in a bundle is a patch: an omitted property is unchanged, null clears it.
vocabulary
The schema a graph accepts: each package's vocab.json, JSON Schema 2020-12 plus a few keywords of its own.
query
One grammar for every list: .task.status=open .priority<=1. A bare word is a text search over the properties marked search: true.

A whole graph in memory, from the packages README:

import { docDoc } from '@yaks/doc'
import { graph } from '@yaks/graph'
import { ram } from '@yaks/ram'
import { loadVocab } from '@yaks/vocab'

let vocab = loadVocab([docDoc])
let g = graph({ storage: ram(vocab), vocab })
await g.apply([{
  entity: { eid: 'first-note' },
  doc: { title: 'Getting started', body: 'A document stored as components.' },
}])
console.log(await g.read('.doc.title="Getting started"'))

Swap ram for @yaks/sqlite to keep it on disk, put @yaks/api in front for HTTP, and use @yaks/client for a browser graph that stays in sync.

Facets: a plugin never says where it runs

A plugin is a package, and each kind of thing it contributes is a subpath export. A process serves roles and imports only the facets of the roles it serves, so a browser tab never loads a database driver and a command line never loads a web server it will not start.

SubpathWhat it exports
./vocabthe package's words: components, tools, effects
./rulesgraph plugins, query compilers, authenticate
./toolsthe code behind its declared tools
./effectsthe code behind what a commit owes
./routesHTTP routes, hosted by @yaks/api
./servicework that keeps going: a clock, a poll, a sweep
./viewsrenderers, for a browser or a terminal
./tuiterminal views for --tui
RoleFacetsWhat the process does
graph./vocab, ./rules, ./toolsopens the file, admits writes, runs tool calls
web./routesanswers HTTP with the routes @yaks/api hosts
effects./effectsclaims and runs what commits owe, in a pool
a plugin's nameits ./servicekeeps that plugin's timer or poll running

Effects are a pool: a commit writes down the runs it owes, and any number of processes claim them. Each service is a singleton, held under a lease named for its package. See @yaks/cli.

The yak command

yak turns each tool a graph declares into a subcommand, with arguments and help from the tool's input schema, so a new tool needs no new CLI release. A config names the database and the plugins: 

{
  "db": "graph.db",
  "plugins": ["@yaks/api", "@yaks/kernel", "@yaks/id",
              "@yaks/doc", "@yaks/task", "@yaks/project"],
  "numbers": true
}
yak --config yak.json task new 'Buy the cake' --priority 1   # task T-1 open
yak --config yak.json task list '.priority<3'
yak --config yak.json serve                                  # @yaks/api's serve tool: HTTP
yak app_list                                                 # a tool on yaks.app's MCP server

Without --config, yak looks for $YAK_CONFIG, then ~/.yak/yak.json, and otherwise talks to https://yaks.app/mcp; --host picks any other MCP server. Local and remote calls both become call entities run through @yaks/tools, so a person and an agent get the same validation, rules, attribution and record. No server is required: SQLite runs in WAL mode, so separate commands and a server share one file.

Sessions and tasks live in the graph

Sessions

A session is an entity, and each transcript entry is an entity beside it: input, a model request, output, a tool call, its result. Status is derived from the entries, never stored. A session holds a claim on the work it is doing, and a second claim on the same entity is refused and recorded. 

yak session new 'reply with the word pong'
yak session send <session> 'and again'
yak session peek <session>

@yaks/harness runs native sessions over any model the @yaks/model interface covers. @yaks/spawn starts claude or codex as a detached process and reads its output back as the session's entries, so a run outlives the process that started it.

Tasks

A task is doc plus task. Its status (open, done, cancelled) is computed from its completed and cancelled marks, by one rule both SQL and the in-memory evaluator use. A board is a saved query, never a stored list, so a task is on a board because it matches. 

yak task new 'Buy the cake' --priority 1
yak task update T-1 done
yak task list '.task.status=done'

Goals, designs, memories and personas are entities too, linked by edges, and every door, from the CLI to MCP to the browser, reads the same vocabulary.

Agents from outside

  • MCP. @yaks/mcp serves the graph at /mcp: five generic tools that take and return bundles, plus every plugin's own tools, each with one output schema, the bundle answer. Claude Code, or any MCP agent, works the same graph a person does.
  • Hooks. yak hooks install writes lifecycle hooks into a Claude-compatible settings file: a starting session is created in the graph under the harness's own id, and an ending one releases its claims.
  • Transcripts. @yaks/session/service follows Claude Code's transcript files and reads them in as sessions, each entry marked with where it came from, so a line read twice writes nothing new.
  • Outward. @yaks/mcp-client reaches a remote MCP server's tools and hands them to a native session like its own.

On your machine, or on Cloudflare

A box

yak serve answers HTTP and WebSocket subscriptions over a SQLite file, and MCP at /mcp when the config lists @yaks/mcp. @yaks/process runs a program so it outlives the server that started it, on Linux and macOS. Secrets live in a vault of private files beside the database.

Cloudflare

@yaks/workerd serves the same handler from a Worker; @yaks/durable-object makes one Durable Object one graph, and @yaks/d1 puts the same storage over D1. One apply(), with the same phases and plugins, runs on all three. The harness's runner names no machine: it runs on a box or in a Worker.

yaks.app: build, host and share web apps

yaks.app is where yaks apps live. A yaks app is an index.html and whatever files sit beside it, served at <space>.yaks.app/<app>/, with no build step. Every app comes with its own store, a graph of entities, and a small client a page imports from ./api/client.js. 

import { apply, query } from './api/client.js'

await apply({ entity: { eid: '$cake' }, doc: { title: 'Lemon cake' } })
let recipes = await query('.doc')
  • People build them by asking Claude or ChatGPT: the connector at https://yaks.app/mcp gives an assistant app_new, app_files and app_deploy, and the same tools are yak commands.
  • A vocab.json beside the page declares the app's own components, and each one gets commands any agent can find later.
  • A worker.js gives an app server code; D1, R2 and Vectorize bindings are created for it at deploy.
  • A space can open a tunnel to your own machine: its apps reach only the paths the machine opened, and the machine needs no open port.

See them working in the demo space: the recipe box. The guide is at yaks.app/docs.md.
